# CLAUDE.md

**Hobbit** : hub interne de l'équipe IT (4 utilisateurs, chargés de projet, non développeurs). Modules : to-do (tâches à cocher, avec sous-tâches, rattachées ou non à un projet, séparées des tickets), notes (bloc-notes personnel en post-it redimensionnables, où l'on transcrit aussi une réunion), assistant Gandalf (chat IA sur les données du hub, bulle en bas à droite), idées d'amélioration (liste priorisée), FAQ (questions et réponses de l'équipe), planning (frise des jalons de tous les projets), projets (suivi complet d'un projet, dont ses tickets ; les cahiers des charges — CDC — se rédigent depuis un projet), tickets (entrée « Tickets » du menu, page `/sprints` : un ou plusieurs tableaux, chacun avec ses sprints, son backlog et ses règles d'affichage ; onglets sprints — planification, tableau du sprint en cours, documents de sprint — et liste de tous les tickets avec recherche), patch note, lecteur de fichiers (fichiers à plat / CSV décrits par des « fiches de lecture » créées par l'IA) suivi TMA (tickets Desk + relevé mensuel du prestataire) et patch management (tests à faire après chaque patch des serveurs et leurs résultats par session). Toute l'interface, les messages d'erreur et les commentaires sont **en français**.

Voir `README.md` (fonctionnalités), `docs/ARCHITECTURE.md` (conception) et `docs/DEPLOIEMENT.md` (AWS).

## Commandes

```bash
pnpm install
pnpm dev             # API :3001 (DynamoDB émulé, enregistré dans apps/api/.data ; IA simulée) + front :5173
pnpm test            # vitest (shared + parcours complet de l'API contre dynalite)
pnpm typecheck
pnpm synth           # synthèse CDK (empaquette aussi les Lambdas) — nécessite apps/web/dist
pnpm export:exemple /tmp   # Word + PDF d'exemple pour contrôler la mise en page
```

## Organisation

Importé en TypeScript source par l'API et le front.
- `apps/api` : Hono. `app.ts` (routes), `db/repo.ts` (tout l'accès DynamoDB/S3), `ai/` (prompts, schémas de sortie, pipeline, fournisseurs Bedrock et simulé), `jobs/runner.ts` (tâches IA asynchrones), `export/` (Word via `docx`, PDF via `pdfmake`). Points d'entrée : `lambda.ts`, `worker.ts`, `local.ts`.
- `apps/api/src/filetypes/` : module lecteur de fichiers (routes, stockage, pipeline IA, jobs).
- `packages/shared/src/tma/` et `apps/api/src/tma/` : module suivi TMA (lecture et masquage des exports — relevé en Excel `parseTmaWorkbook` ou en PDF `parseTmaPdf`, tableau reconstitué par `files/pdfTable.ts` à partir du texte que pdf.js extrait dans le navigateur, `tma/pdf.ts` —, calcul des rapports ; stockage, classement par thème et synthèse IA). - `apps/api/src/projects/` : module projets (routes génériques par type d'élément, stockage `PROJ#…` — les tickets sont les éléments `tasks`, le temps passé hors ticket les éléments `times`, total par `projectSpentHours` —, IA : analyse de réunion, rapport d'avancement, contexte projet pour la génération de CDC).
- Tableaux de tickets (`packages/shared/src/sprints/boards.ts`, `apps/api/src/sprints/boards.ts` + `boardRoutes.ts` sous `/api/boards`, onglet « Tableaux » du paramétrage `settings/BoardsTab.tsx`, crochets `sprints/boards.tsx`) : partition `BOARD` ; un ticket et un sprint ont un `boardId` (absent : `DEFAULT_BOARD_ID`, lu par `boardOf` / `normalizeTaskRecord`), un sprint en cours par tableau ; création/renommage/suppression (tableau vide seulement, jamais le principal) par le droit `manageBoards`, règles d'affichage (`cardRules`, dont la règle `type`) par tableau et par toute l'équipe (`PUT /api/boards/:id/regles` ; le principal, jamais enregistré, reprend `cardRules` de l'ancien paramétrage). Tableau par défaut de chacun : `defaultBoardId` de sa fiche (`PUT /api/me/preferences`). Le serveur place le ticket (`placeTicket`, appelé par `pr.createItem` / `pr.updateItem`) : créé sans tableau → tableau par défaut de qui le crée ; planifié dans un sprint → tableau du sprint ; changé de tableau → quitte un sprint de l'ancien. La page Tickets (`?tableau=`) passe son tableau à la fiche du ticket (`defaults.boardId`).

Front : `apps/web/src/sprints/` (page `/sprints`, « Tickets » dans le menu : onglet Sprints — tableau, planification, backlog — et onglet « Tous les tickets » `AllTickets.tsx` via `GET /api/sprints/tickets` ; page d'un sprint ; composants de ticket `tickets.tsx`).

## Règles à respecter

- **Coûts IA** : tout appel passe par `callStructured` (suivi + budget). Jamais d'appel IA automatique : uniquement sur action explicite. Envoyer au modèle le strict nécessaire (sections utiles, Markdown plutôt que JSON) ; modèle rapide (`fast`) pour le volumineux et le mécanique, `smart` pour la rédaction. Garder les prompts système sans données variables (cache de prompt).
- Bedrock est appelé par `@anthropic-ai/bedrock-sdk` avec sorties structurées (`messages.parse` + `zodOutputFormat`) : par défaut `AnthropicBedrock` (InvokeModel, `bedrock-runtime`, région Paris, modèles appelés par leur profil d'inférence européen `eu.anthropic.claude-…-5-5`, `bedrockApi: runtime`), sinon `AnthropicBedrockMantle` (`bedrock-mantle`, absent de Paris : « Connection error »). Noms exacts des profils : `aws bedrock list-inference-profiles --region eu-west-3`. Un échec d'appel s'affiche en clair (`bedrockError`). Pas de `tool_choice` forcé, pas de `budget_tokens`, pas de prefill (refusés par les modèles actuels) : régler `output_config.effort`.
- Le document : `contexte` unique et en premier, `annexes` unique et en dernier (`normalizeSections`, `cdcDocumentSchema`). L'IA ne peut ni supprimer une section ni toucher une section qu'on ne lui a pas montrée (`applyUpdate`).
- Versions immuables ; tout enregistrement passe par `repo.saveVersion` avec `baseSeq` (verrouillage optimiste). Pas d'enregistrement pendant un job actif.
- Lecteur de fichiers : les fichiers des utilisateurs sont lus **dans le navigateur** et ne doivent jamais être envoyés au serveur. Seul l'extrait (anonymisé par défaut, `anonymizeLine`) et la documentation partent à l'IA. L'IA produit une fiche déclarative (`fileSpecSchema`), jamais du code ; ses sorties passent par `sanitizeSpec`/`applyPatch`. Les jobs IA ciblent un élément via `targetId` (CDC ou type de fichier).
- Assistant : sur action explicite seulement, modèle `fast`, synchrone (`timeoutMs` sous la limite de 29 s de l'API). Les données sont rassemblées par le code (`globalContext`, en `context` mis en cache ; projets cités via `mentionedProjects`) ; n'y envoyer que ce que l'utilisateur voit : jamais les notes ni la to-do personnelle des autres. Il ne modifie rien lui-même : d'un long texte collé (`ASSISTANT_QUESTION_MAX` ; les échanges précédents repartent abrégés à `ASSISTANT_HISTORY_CHARS`), il propose des `actions` (ticket, to-do, jalon, `projet` — nouveau projet : nom, domaine du paramétrage, chef de projet, fin visée, jamais un doublon —, et `ticket_update` : mise à jour d'un ticket existant désigné par sa clé, avec avant → après dans `update`) filtrées par `sanitizeActions` (projet existant, date valide, ticket ouvert existant et changement réel), et commence sa réponse par son plan (« Après analyse, je vais… ») ; le navigateur les crée au clic « Créer » par les routes habituelles (`assistant/actions.tsx`). Pièces jointes (`attachments` de `assistantAskBody`, `assistant/attachments.ts`) : images (collées, glissées, réduites dans le navigateur) et PDF envoyés au modèle avec cette seule question (`StructuredCall.attachments`, blocs avant le texte), Word/Excel/texte lus dans le navigateur et ajoutés à la question ; jamais gardés ni renvoyés avec l'historique. Une page lui confie un texte par `openGandalf(text)` ou le bouton `GandalfActionsButton` (notes, entrées du journal ; envoi toujours au clic). Sur une demande directe (« crée-moi un ticket… »), il propose l'élément : type de ticket du paramétrage (`ticketType`, vérifié par `sanitizeActions`, devient le champ `type` du ticket), priorité, responsable actif (`assigneeId`) ; le contexte liste l'équipe, les types de tickets, les domaines de projet et la FAQ.
- **L'IA propose, l'utilisateur valide** : un traitement IA qui crée ou modifie des éléments du hub enregistre une proposition, avec son plan en clair (« Après analyse, je vais créer…, mettre à jour… »), jamais le changement lui-même. Compte rendu de réunion : `suggestions` de la note (`plan`, tickets à créer, `ticketUpdates` sur les tickets ouverts — `ticketUpdatesOf` —, jalons, risques), appliquées par `POST /api/projects/:id/notes/:noteId/suggestions`. Classement TMA : proposition `TMA#DESK`/`PROPOSAL` (`ThemeProposal`, plan `themePlan`, détail dans le bucket), appliquée par `POST /api/tma/desk/proposition/apply` ou abandonnée par `DELETE` (front `tma/ThemeProposalCard.tsx`). Gandalf : cartes d'action, une par proposition.
- Projets : un CDC est rattaché par `projectId` (fiche CDC, hors document versionné) et se crée via `POST /api/projects/:id/cdcs`. Les propositions de l'assistant (tickets, jalons, risques d'un compte rendu) ne sont jamais ajoutées sans validation explicite. Les champs texte des projets sont en Markdown (`MarkdownField` / `MarkdownView` côté front).
- Paramétrage (`settings.ts`, `apps/api/src/settings/`, `apps/web/src/settings/`) : afficher les statuts via `useSettings()` / `StatusOptions` (front) ou `getLists()` (API), jamais via les constantes `*_STATUS_LABELS`. Les codes de statut ne changent pas. Une prestation doit référencer un prestataire du paramétrage (`resolveProjectRefs`) ; toute nouvelle copie d'une donnée du référentiel doit être tenue à jour par `syncItems`.
- Suivi TMA : exports Desk et relevés lus **dans le navigateur** ; seuls les champs utiles partent au serveur, textes passés par `maskPersonalData`. Les chiffres sont calculés par le code (`report.ts`) ; l'IA ne reçoit que des agrégats pour la synthèse, et chaque ticket n'est classé qu'une fois ; son classement est une proposition à valider (voir « L'IA propose, l'utilisateur valide »). Le temps des relevés s'ajoute aux contacts des prestataires du même nom (`matchTmaPeople`, calculé à la lecture par `tmaHoursByContact`) ; les intervenants inconnus sont signalés (`unknownPeople`). Ne jamais committer de vrais exports (données personnelles) : fixtures fictives dans `packages/shared/test/fixtures/tma.ts`.
- To-do : une nouvelle tâche est pour aujourd'hui par défaut (`defaultDueDate`, posé par le front : saisie rapide et fiche) ; une tâche se coche (`done`), pas de statut, de priorité ni de sprint ; son ordre (glisser-déposer) est le rang `position`, modifié seulement par `PUT /api/todos/ordre` ; elle se rattache ou non à un projet (`projectId`) et **ne crée jamais de ticket** : to-do et tickets sont deux choses séparées. Ses sous-tâches (`subtasks`, cochées à part) sont enregistrées avec elle et remplacées en entier par le `PATCH`. La to-do d'un projet est partagée par l'équipe. Les tickets, eux, ont un statut : lire leurs anciens enregistrements (tâches à cocher) via `normalizeTaskRecord`.
- Notes : personnelles (partition `NOTE#<e-mail>` du titulaire) ; seuls les administrateurs (droit `manageAllNotes`) lisent celles des autres et leur en ajoutent (`?user=`, `ownerId`, `?owner=`). Une note s'archive (`archived`) au lieu d'être supprimée. Sa taille de post-it (`width`, `height`) ne compte pas comme une modification (`NOTE_LAYOUT_FIELDS`). Supprimer un projet détache ses tâches de to-do et ses notes.
- Chefs de projet : un ou plusieurs utilisateurs du hub (`chefDeProjetIds`, noms recopiés séparés par des virgules dans `chefDeProjet`) : passer par `resolveProjectChefs` à la création et à la modification ; l'ancien champ unique `chefDeProjetId` est lu par `normalizeChefIds` (retiré au premier enregistrement), les anciens projets saisis en texte sont rattachés par `linkLegacyChefs`. Suivi d'un projet : `followers` (hors fiche, `PUT /api/projects/:id/suivi`). « Mes projets » = l'un des chefs de projet ou suivi (`isMyProject`) ; le filtre est partagé par les pages liées aux projets (`projects/mine.tsx`, `useMyProjectsFilter`).
- Statut d'un projet et frise d'avancement : `PROJECT_STEPS` (cadrage → planifié → en cours → recette → production → terminé, `projectStepIndex`, composant `ProjectSteps` de `projects/common.tsx`, accueil et page projet ; chaque flèche a la couleur du badge `pstatus-*` de son statut ; sur la page du projet, un clic sur une flèche y passe le projet : `onSelect`) ; les autres statuts sont hors frise. Le blocage n'est pas un statut : `blocked` + `blockedReason` (fiche), le projet reste à son étape. Domaines d'un projet : `domains`, choisis parmi `projectDomains` du paramétrage (`DomainChoices`) ; un domaine ajouté aux valeurs par défaut va aussi dans `ADDED_PROJECT_DOMAINS` (ajouté une fois à un paramétrage enregistré, `getLists`). Un statut ajouté au domaine est placé après son prédécesseur dans un paramétrage déjà enregistré (`normalizeListSettings`).
- Process complet : `POST /api/projects/:id/tickets/process` (`ticketProcessBody`) crée un ticket par étape de `TICKET_PROCESS_STEPS`, dans l'ordre (`ticketProcessTickets` : type, titre, le premier « À faire », les suivants « En attente » ; front : `projects/TicketProcessDialog.tsx`). Quand un ticket du process est terminé (détecté dans `api.updateItem`, évènement `TICKET_DONE`), `projects/ProcessNextDialog.tsx` (monté dans `Layout`) propose l'étape suivante (`PROCESS_NEXT` : statut du projet, ticket suivant) ; rien sans clic : `POST /api/projects/:id/tickets/:itemId/suite` (`processNextBody`), puis `PROJECT_CHANGED` met à jour les pages ouvertes.
- Fiche projet et CDC : après l'enregistrement de la description ou des sections d'un projet qui a des CDC, la fiche propose de les reporter (`CdcSyncCard` de `OverviewTab.tsx`) : `POST /api/projects/:id/cdcs/sync` (`syncProjectCdcsBody`, `applyProjectToCdc` : Contexte et sections de même titre, une nouvelle version par CDC par `repo.saveVersion`, aucune section supprimée). Date de fin visée : jalon « Fin du projet » (`TARGET_JALON_LABEL`) créé et déplacé par `syncTargetJalon`.
- Validation d'un CDC (`packages/shared/src/cdcReview.ts`, `apps/api/src/cdcReviews/routes.ts`, onglet « Validations » `cdc/ReviewsPanel.tsx`, page publique `cdc/PublicReviewPage.tsx` rendue hors `AuthGate` pour `/validation/<jeton>`) : un lien personnel par destinataire (du hub ou non), envoyé par e-mail (`lib/mail.ts` : SES avec `MAIL_FROM`, sinon écrit dans `.data/emails` en local ; le lien est aussi montré une fois au demandeur). Seule l'empreinte du jeton est enregistrée. Les routes `/api/public/*` sont les seules sans connexion (montées avant `authMiddleware`, route API Gateway sans autorisateur) : n'y exposer que ce qu'un jeton valide et l'adresse du destinataire permettent de voir. Réponse non bloquante (validé ou non + commentaire), le CDC n'est jamais modifié.
- Jalons : ponctuels (`date`) ou sur une période (`startDate` → `date`) ; retard et glissement se mesurent sur `date`. Utilisateurs : poste, backup (autre utilisateur actif), périmètres (`PERIMETERS`).
- Sprints : un ticket appartient à un projet (élément `tasks`) ou est hors projet (`NO_PROJECT_ID`, sans fiche : pas d'activité ni d'indicateurs ; dans les formulaires, « Aucun projet » = valeur vide, jamais d'option « Hors projet » à choisir) ; un type facultatif (champ `type`, parmi les `ticketTypes` du paramétrage, comparé par `ticketTypeKey`, affiché par `TicketTypeBadge` ; les anciens tickets l'avaient en préfixe du titre « [DEV] - … » : `normalizeTaskRecord` le lit et le retire du titre, et un `PATCH` du seul titre garde le type) ; changer son projet passe par `projectId` dans le `PATCH` (`moveTicket`, numéro et historique conservés) ; il se rattache au ticket Desk du prestataire par `deskId` (comparer avec `deskKey`) ; le temps des relevés TMA de ce ticket Desk s'ajoute à son temps passé (`tmaHours`, part tenue par `syncTmaHours` / `withTmaHours`, jamais saisie), a un numéro (`T-12`), une priorité (`PRIORITIES`, tri `byTicketPriority`), un temps estimé et un temps passé indépendants (`estimatedHours`, `spentHours` en heures, null : non renseigné ; saisis et affichés en jours de 8 h et heures par `parseDuration` / `formatDuration`, `sprints/duration.ts`), un statut (`TICKET_STATUSES`) et un sprint (`sprintId`, null = backlog). Notes de suivi d'un ticket : `comments` (hors champs du ticket, conservées par `derived` et `moveTicket`), seulement par `POST|PUT|DELETE /api/projects/:id/tickets/:itemId/notes` (`addTicketComment`, `changeTicketComment` : l'auteur seul modifie ou supprime) ; jamais envoyées à l'IA. Le serveur tient l'historique (`statusChanges`, `sprintChanges`) dont dépend la revue de sprint : ne changer le statut ou le sprint d'un ticket que par `pr.createItem` / `pr.updateItem`. Un seul sprint en cours par tableau ; on ne planifie que dans un sprint en cours ou à venir (`assertPlannable`). Un sprint dont la fin est passée (`isPastSprint`) ne se démarre ni ne se prépare : enregistré clos à la création, ou classé par `POST /api/sprints/:id/past`. Chiffres calculés par `buildSprintReport` / `buildSprintPreparation` ; l'IA ne reçoit que `sprintReportToMarkdown` / `sprintPreparationToMarkdown` (pas les descriptions).
- Utilisateurs : tester un droit (`can`, `requirePermission`, `me.permissions` côté front), jamais un rôle. Les tickets portent `assigneeId` (utilisateur) et le nom recopié `assignee` : passer par `resolveTaskAssignee` pour toute création ou modification. Garder au moins un administrateur actif.
- Images : uniquement PNG/JPEG (formats communs Word + PDF), référencées `asset:<cdcId>/<assetId>` dans un CDC, `asset:hub/<assetId>` ailleurs (`POST /api/images`, `HUB_ASSET_SCOPE` ; description d'un ticket : `MarkdownField images`, affichées aussi par `MarkdownView`).
- Notifications Teams (`packages/shared/src/notifications.ts`, `apps/api/src/notifications/`, onglet « Teams » du paramétrage `settings/TeamsTab.tsx`, droit `manageIntegrations`) : une connexion pour le hub, adresse d'un flux Workflows (`REF#TEAMS`, jamais renvoyée en entier au front ; hôtes limités par `teamsWebhookError`). Pour une nouvelle notification : l'ajouter à `NOTIFICATION_EVENTS` puis appeler `notify(event, message)` après l'action (ne lève jamais d'erreur, échec noté dans `lastError`). Mise en production (`mise_en_prod`) : le build du front écrit `patch-notes.json`, le déploiement le transmet au worker (`AnnounceRelease` dans `hub-stack.ts`, rejouée quand le patch note change ; évènement `{ release }`), qui n'annonce que les entrées d'après la dernière annoncée (`notifyRelease`, `REF#TEAMS`/`RELEASE`). Le canal est lu par toute l'équipe : n'y envoyer que ce que tous voient (jamais notes, to-do personnelle, retours).
- Choix multiple dans une liste (chefs de projet…) : `MultiSelect` (`components/ui.tsx`, liste déroulante maison avec étiquettes et filtre), via `UserChoices` pour les utilisateurs.
- Les tests de l'API (`apps/api/test/cdc.test.ts`, `filetypes.test.ts`, `projects.test.ts`, `settings.test.ts`, `tma.test.ts`, `sprints.test.ts`, `users.test.ts`, `notes.test.ts`, `feedback.test.ts`, `notifications.test.ts`, `anneau.test.ts`, `ideas.test.ts`, `patch.test.ts`, `faq.test.ts`, `boards.test.ts`, `assistant.test.ts`, `cdcReviews.test.ts`) et du moteur de lecture (`packages/shared/test/files.test.ts`, `tma.test.ts`, `sprints.test.ts`, `patch.test.ts`, fichier de démonstration `fixtures/demo.ww`) couvrent les parcours complets : les compléter à chaque évolution.

## Pièges connus

- Lambdas empaquetées en **CommonJS** : pdfkit (sous pdfmake) charge ses polices via des imports `#standard-fonts/*` dynamiques ; `hub-stack.ts` copie ces modules à côté du bundle (`commandHooks.afterBundling`). Ne pas passer en ESM sans revoir ce point (pdfkit utilise aussi `__filename`).
- En local, dynalite enregistre la base sur disque (`apps/api/.data/dynamodb`, avec les fichiers dans `apps/api/.data`) ; `LOCAL_DB=memoire` pour une base vide à chaque démarrage. Un seul processus API à la fois (verrou LevelDB). Les tests utilisent toujours une base en mémoire.
- Mesurer les performances du moteur de lecture sur un bundle (esbuild/Vite), pas via `tsx` : `tsx` est 4 à 5 fois plus lent.
- `RichEditor` : n'émettre `onChange` que si `transaction.docChanged` (sinon `setEditable` marque le document comme modifié).
- Responsive : sous 900 px le menu devient un tiroir (`Layout.tsx`), sous 640 px les tableaux `.table-wrap` passent en cartes (libellés posés automatiquement par `useResponsiveTables` ; ajouter `table-scroll` pour garder un tableau défilant) et les modales s'ouvrent en bas d'écran.
- Le front charge `/config.json` (généré au déploiement) ; en local, son absence active le mode `dev` (pas de Cognito : page de connexion sans mot de passe, en-tête `x-dev-user`). Les tests de l'API créent l'annuaire à la volée : le premier utilisateur d'un fichier de test est administrateur.
