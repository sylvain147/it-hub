# CLAUDE.md

**Hobbit** : hub interne de l'équipe IT (4 utilisateurs, chargés de projet, non développeurs). Modules : to-do (tâches à cocher, avec sous-tâches, rattachées ou non à un projet, séparées des tickets), notes (bloc-notes personnel en post-it redimensionnables), assistant Gandalf (chat IA sur les données du hub, bulle en bas à droite), idées d'amélioration (liste priorisée), transcription de réunion, planning (frise des jalons de tous les projets), projets (suivi complet d'un projet, dont ses tickets ; les cahiers des charges — CDC — se rédigent depuis un projet), sprints (planification des tickets, tableau du sprint en cours, documents de sprint), lecteur de fichiers (fichiers à plat / CSV décrits par des « fiches de lecture » créées par l'IA) et suivi TMA (tickets Desk + relevé mensuel du prestataire). Toute l'interface, les messages d'erreur et les commentaires sont **en français**.

Voir `README.md` (fonctionnalités), `docs/ARCHITECTURE.md` (conception) et `docs/DEPLOIEMENT.md` (AWS).

## Commandes

```bash
pnpm install
pnpm dev             # API :3001 (DynamoDB émulé, enregistré dans apps/api/.data ; IA simulée) + front :5173
pnpm test            # vitest (shared + parcours complet de l'API contre dynalite)
pnpm typecheck
pnpm synth           # synthèse CDK (empaquette aussi les Lambdas) — nécessite apps/web/dist
pnpm export:exemple /tmp   # Word + PDF d'exemple pour contrôler la mise en page
```

## Organisation

- `packages/shared` : types et schémas zod du domaine (`cdc.ts`, `project.ts` pour les projets et leurs éléments rattachés + `computeStats`), corps des requêtes (`api.ts`), conversion Markdown ⇄ JSON TipTap (`markdown.ts`), et pour le lecteur de fichiers `files/` (fiche `spec.ts`, moteur `parse.ts`, extrait anonymisé `excerpt.ts`, lecture/écriture Excel `xlsx.ts`). Importé en TypeScript source par l'API et le front.
- `apps/api` : Hono. `app.ts` (routes), `db/repo.ts` (tout l'accès DynamoDB/S3), `ai/` (prompts, schémas de sortie, pipeline, fournisseurs Bedrock et simulé), `jobs/runner.ts` (tâches IA asynchrones), `export/` (Word via `docx`, PDF via `pdfmake`). Points d'entrée : `lambda.ts`, `worker.ts`, `local.ts`.
- `apps/api/src/filetypes/` : module lecteur de fichiers (routes, stockage, pipeline IA, jobs).
- `packages/shared/src/tma/` et `apps/api/src/tma/` : module suivi TMA (lecture et masquage des exports, calcul des rapports ; stockage, classement par thème et synthèse IA). Front : `apps/web/src/tma/`.
- `apps/api/src/projects/` : module projets (routes génériques par type d'élément, stockage `PROJ#…` — les tickets sont les éléments `tasks` —, IA : analyse de réunion, rapport d'avancement, contexte projet pour la génération de CDC).
- `packages/shared/src/sprints/` et `apps/api/src/sprints/` : module sprints (sprints `SPRINT`, démarrage, clôture ; revue `report.ts` et préparation `preparation.ts` d'un sprint, documents IA). Front : `apps/web/src/sprints/` (page `/sprints` : tableau, planification, backlog ; page d'un sprint ; composants de ticket `tickets.tsx`).
- `packages/shared/src/users.ts`, `apps/api/src/users/` et `apps/web/src/users/` : utilisateurs, rôles et droits, to-do (page « To-do » `/todo`, onglet « To-do et notes » d'un projet `projects/TodoTab.tsx`). Composants de la to-do (liste à cocher, fiche, choix du projet) : `apps/web/src/tasks/tasks.tsx`.
- `packages/shared/src/notes.ts`, `apps/api/src/notes/routes.ts` et `apps/web/src/notes/` : notes en vrac personnelles (page `/notes`). Frise globale des jalons : `GET /api/projects/jalons`, `apps/web/src/projects/GlobalPlanningPage.tsx` (page `/planning`). Connexion : `apps/web/src/auth.tsx` + `auth/LoginPage.tsx`.
- Thème de couleur par utilisateur : `packages/shared/src/themes.ts` (`THEMES`, `THEME_DEFS`, champ `theme` de la fiche, `PUT /api/me/preferences`), `apps/web/src/theme.ts` (`applyTheme` remplace les variables CSS `--navy`, `--navy-2`, `--blue`, `--blue-50`) et `users/ThemeModal.tsx`. Les styles n'emploient que ces variables pour l'accent, jamais de bleu en dur. Thème par défaut : `comte` (vert, aussi dans `:root` de `styles.css`). Logo : `apps/web/public/hobbit.png` (+ `favicon.png`, `apple-touch-icon.png`) ; logo + nom « Hobbit » (police Almendra auto-hébergée, brin de feuilles en SVG) : `components/Brand.tsx`.
- `packages/shared/src/feedback.ts`, `apps/api/src/feedback/` et `apps/web/src/feedback/` : retours sur l'application (« Faire un retour » dans le menu de l'utilisateur, page « Retours » réservée au droit `manageFeedback`).
- `packages/shared/src/bouton.ts`, `apps/api/src/bouton/routes.ts` et `apps/web/src/bouton/BoutonRouge.tsx` : petit jeu caché du bouton rouge « NE PAS CLIQUER » (apparition au hasard, compteur de clics par utilisateur ; `?bouton-rouge` le force ; classement complet sur `/mur-de-la-honte`, page sans lien).
- `packages/shared/src/ideas.ts`, `apps/api/src/ideas/routes.ts` et `apps/web/src/ideas/IdeasPage.tsx` : idées d'amélioration (partition `IDEA`, page `/idees`) ; une idée devient un ticket par `POST /api/idees/:id/ticket`.
- `packages/shared/src/assistant.ts`, `apps/api/src/assistant/` (`context.ts` : données mises en forme par le code ; `routes.ts` : `POST /api/assistant`, synchrone) et `apps/web/src/assistant/Gandalf.tsx` : assistant « Gandalf », chat IA global (bulle volante en bas à droite de chaque page, icône `apps/web/public/gandalf.png`, chat en surimpression ; conversation gardée dans le `sessionStorage`). Pas d'entrée de menu ; `/assistant` redirige vers l'accueil.
- `apps/web/src/meetings/` : transcription de réunion en direct (page `/reunion`, reconnaissance vocale du navigateur, aucun son enregistré ; fournisseur global `MeetingRecorderProvider` pour continuer d'une page à l'autre). Le compte rendu passe par l'analyse de réunion existante (`POST /api/projects/:id/digest`).
- `apps/web/src/tasks/TodoBadge.tsx` : pastille de l'entrée « To-do » du menu (tâches du jour ou en retard ; les mutations de la to-do émettent `TODOS_CHANGED` dans `api.ts`). La fiche d'une tâche crée un projet sans la quitter (`projects/NewProjectDialog.tsx`, `onCreated`).
- `apps/web` : React + Vite + TipTap. `projects/` contient la liste et la page projet (un fichier par onglet, contexte partagé dans `common.tsx`), `cdc/CdcEditorPage.tsx` l'éditeur de CDC, `files/` le lecteur de fichiers ; `modules.ts` liste les modules du hub et leur section du menu (`MENU_SECTIONS`). Garder le menu court : une entrée par module, quatre au plus par section, `menu: false` pour ce qui est accessible ailleurs ; l'administration (`ADMIN_LINKS`) est dans le menu de l'utilisateur, en bas du menu latéral.
- `infra` : CDK. `lib/hub-stack.ts` (tout le hub), `lib/github-oidc-stack.ts` (rôle de déploiement GitHub).

## Règles à respecter

- **Coûts IA** : tout appel passe par `callStructured` (suivi + budget). Jamais d'appel IA automatique : uniquement sur action explicite. Envoyer au modèle le strict nécessaire (sections utiles, Markdown plutôt que JSON) ; modèle rapide (`fast`) pour le volumineux et le mécanique, `smart` pour la rédaction. Garder les prompts système sans données variables (cache de prompt).
- Bedrock est appelé via `AnthropicBedrockMantle` (`@anthropic-ai/bedrock-sdk`) avec sorties structurées (`messages.parse` + `zodOutputFormat`). Pas de `tool_choice` forcé, pas de `budget_tokens`, pas de prefill (refusés par les modèles actuels) : régler `output_config.effort`.
- Le document : `contexte` unique et en premier, `annexes` unique et en dernier (`normalizeSections`, `cdcDocumentSchema`). L'IA ne peut ni supprimer une section ni toucher une section qu'on ne lui a pas montrée (`applyUpdate`).
- Versions immuables ; tout enregistrement passe par `repo.saveVersion` avec `baseSeq` (verrouillage optimiste). Pas d'enregistrement pendant un job actif.
- Lecteur de fichiers : les fichiers des utilisateurs sont lus **dans le navigateur** et ne doivent jamais être envoyés au serveur. Seul l'extrait (anonymisé par défaut, `anonymizeLine`) et la documentation partent à l'IA. L'IA produit une fiche déclarative (`fileSpecSchema`), jamais du code ; ses sorties passent par `sanitizeSpec`/`applyPatch`. Les jobs IA ciblent un élément via `targetId` (CDC ou type de fichier).
- Assistant : sur action explicite seulement, modèle `fast`, synchrone (`timeoutMs` sous la limite de 29 s de l'API). Les données sont rassemblées par le code (`globalContext`, en `context` mis en cache ; projets cités via `mentionedProjects`) ; n'y envoyer que ce que l'utilisateur voit : jamais les notes ni la to-do personnelle des autres. Il ne modifie rien.
- Projets : un CDC est rattaché par `projectId` (fiche CDC, hors document versionné) et se crée via `POST /api/projects/:id/cdcs`. Les propositions de l'assistant (tickets, jalons, risques d'un compte rendu) ne sont jamais ajoutées sans validation explicite. Les champs texte des projets sont en Markdown (`MarkdownField` / `MarkdownView` côté front).
- Paramétrage (`settings.ts`, `apps/api/src/settings/`, `apps/web/src/settings/`) : afficher les statuts via `useSettings()` / `StatusOptions` (front) ou `getLists()` (API), jamais via les constantes `*_STATUS_LABELS`. Les codes de statut ne changent pas. Une prestation doit référencer un prestataire du paramétrage (`resolveProjectRefs`) ; toute nouvelle copie d'une donnée du référentiel doit être tenue à jour par `syncItems`.
- Suivi TMA : exports Desk et relevés lus **dans le navigateur** ; seuls les champs utiles partent au serveur, textes passés par `maskPersonalData`. Les chiffres sont calculés par le code (`report.ts`) ; l'IA ne reçoit que des agrégats pour la synthèse, et chaque ticket n'est classé qu'une fois. Le temps des relevés s'ajoute aux contacts des prestataires du même nom (`matchTmaPeople`, calculé à la lecture par `tmaHoursByContact`) ; les intervenants inconnus sont signalés (`unknownPeople`). Ne jamais committer de vrais exports (données personnelles) : fixtures fictives dans `packages/shared/test/fixtures/tma.ts`.
- To-do : une tâche se coche (`done`), pas de statut, de priorité ni de sprint ; son ordre (glisser-déposer) est le rang `position`, modifié seulement par `PUT /api/todos/ordre` ; elle se rattache ou non à un projet (`projectId`) et **ne crée jamais de ticket** : to-do et tickets sont deux choses séparées. Ses sous-tâches (`subtasks`, cochées à part) sont enregistrées avec elle et remplacées en entier par le `PATCH`. La to-do d'un projet est partagée par l'équipe. Les tickets, eux, ont un statut : lire leurs anciens enregistrements (tâches à cocher) via `normalizeTaskRecord`.
- Notes : personnelles (partition `NOTE#<e-mail>` du titulaire) ; seuls les administrateurs (droit `manageAllNotes`) lisent celles des autres et leur en ajoutent (`?user=`, `ownerId`, `?owner=`). Une note s'archive (`archived`) au lieu d'être supprimée. Sa taille de post-it (`width`, `height`) ne compte pas comme une modification (`NOTE_LAYOUT_FIELDS`). Supprimer un projet détache ses tâches de to-do et ses notes.
- Chefs de projet : un ou plusieurs utilisateurs du hub (`chefDeProjetIds`, noms recopiés séparés par des virgules dans `chefDeProjet`) : passer par `resolveProjectChefs` à la création et à la modification ; l'ancien champ unique `chefDeProjetId` est lu par `normalizeChefIds` (retiré au premier enregistrement), les anciens projets saisis en texte sont rattachés par `linkLegacyChefs`. Suivi d'un projet : `followers` (hors fiche, `PUT /api/projects/:id/suivi`). « Mes projets » = l'un des chefs de projet ou suivi (`isMyProject`) ; le filtre est partagé par les pages liées aux projets (`projects/mine.tsx`, `useMyProjectsFilter`).
- Jalons : ponctuels (`date`) ou sur une période (`startDate` → `date`) ; retard et glissement se mesurent sur `date`. Utilisateurs : poste, backup (autre utilisateur actif), périmètres (`PERIMETERS`).
- Sprints : un ticket appartient à un projet (élément `tasks`) ou est hors projet (`NO_PROJECT_ID`, sans fiche : pas d'activité ni d'indicateurs ; dans les formulaires, « Aucun projet » = valeur vide, jamais d'option « Hors projet » à choisir) ; à la création, un type facultatif (`ticketTypes` du paramétrage) propose le titre « [DEV] - Nom du projet » (`ticketTypeTitle`, `withTicketType`) : le type n'est pas un champ, il n'existe que dans le titre ; changer son projet passe par `projectId` dans le `PATCH` (`moveTicket`, numéro et historique conservés) ; il se rattache au ticket Desk du prestataire par `deskId` (comparer avec `deskKey`) ; le temps des relevés TMA de ce ticket Desk s'ajoute à son temps passé (`tmaHours`, part tenue par `syncTmaHours` / `withTmaHours`, jamais saisie), a un numéro (`T-12`), une priorité (`PRIORITIES`, tri `byTicketPriority`), un temps estimé et un temps passé indépendants (`estimatedHours`, `spentHours` en heures, null : non renseigné), un statut (`TICKET_STATUSES`) et un sprint (`sprintId`, null = backlog). Le serveur tient l'historique (`statusChanges`, `sprintChanges`) dont dépend la revue de sprint : ne changer le statut ou le sprint d'un ticket que par `pr.createItem` / `pr.updateItem`. Un seul sprint en cours ; on ne planifie que dans un sprint en cours ou à venir (`assertPlannable`). Un sprint dont la fin est passée (`isPastSprint`) ne se démarre ni ne se prépare : enregistré clos à la création, ou classé par `POST /api/sprints/:id/past`. Chiffres calculés par `buildSprintReport` / `buildSprintPreparation` ; l'IA ne reçoit que `sprintReportToMarkdown` / `sprintPreparationToMarkdown` (pas les descriptions).
- Utilisateurs : tester un droit (`can`, `requirePermission`, `me.permissions` côté front), jamais un rôle. Les tickets portent `assigneeId` (utilisateur) et le nom recopié `assignee` : passer par `resolveTaskAssignee` pour toute création ou modification. Garder au moins un administrateur actif.
- Images : uniquement PNG/JPEG (formats communs Word + PDF), référencées `asset:<cdcId>/<assetId>` dans un CDC, `asset:hub/<assetId>` ailleurs (`POST /api/images`, `HUB_ASSET_SCOPE` ; description d'un ticket : `MarkdownField images`, affichées aussi par `MarkdownView`).
- Choix multiple dans une liste (chefs de projet…) : `MultiSelect` (`components/ui.tsx`, liste déroulante maison avec étiquettes et filtre), via `UserChoices` pour les utilisateurs.
- Les tests de l'API (`apps/api/test/cdc.test.ts`, `filetypes.test.ts`, `projects.test.ts`, `settings.test.ts`, `tma.test.ts`, `sprints.test.ts`, `users.test.ts`, `notes.test.ts`, `feedback.test.ts`, `bouton.test.ts`, `ideas.test.ts`, `assistant.test.ts`) et du moteur de lecture (`packages/shared/test/files.test.ts`, `tma.test.ts`, `sprints.test.ts`, fichier de démonstration `fixtures/demo.ww`) couvrent les parcours complets : les compléter à chaque évolution.

## Pièges connus

- Lambdas empaquetées en **CommonJS** : pdfkit (sous pdfmake) charge ses polices via des imports `#standard-fonts/*` dynamiques ; `hub-stack.ts` copie ces modules à côté du bundle (`commandHooks.afterBundling`). Ne pas passer en ESM sans revoir ce point (pdfkit utilise aussi `__filename`).
- En local, dynalite enregistre la base sur disque (`apps/api/.data/dynamodb`, avec les fichiers dans `apps/api/.data`) ; `LOCAL_DB=memoire` pour une base vide à chaque démarrage. Un seul processus API à la fois (verrou LevelDB). Les tests utilisent toujours une base en mémoire.
- Mesurer les performances du moteur de lecture sur un bundle (esbuild/Vite), pas via `tsx` : `tsx` est 4 à 5 fois plus lent.
- `RichEditor` : n'émettre `onChange` que si `transaction.docChanged` (sinon `setEditable` marque le document comme modifié).
- Responsive : sous 900 px le menu devient un tiroir (`Layout.tsx`), sous 640 px les tableaux `.table-wrap` passent en cartes (libellés posés automatiquement par `useResponsiveTables` ; ajouter `table-scroll` pour garder un tableau défilant) et les modales s'ouvrent en bas d'écran.
- Le front charge `/config.json` (généré au déploiement) ; en local, son absence active le mode `dev` (pas de Cognito : page de connexion sans mot de passe, en-tête `x-dev-user`). Les tests de l'API créent l'annuaire à la volée : le premier utilisateur d'un fichier de test est administrateur.
